Analytical Development

Analyze how the method has behaved across every run, not the last one

An agent that reads system suitability from every injection since validation, segments it by column, instrument, analyst and standard lot, and tells you which of those the drift actually follows.

What this looks like today

System suitability passes right up until the method investigation.

A method is validated, transferred and put into routine use. Every run passes system suitability, so nothing raises a flag. Underneath that, the standard response has been creeping down for eight months, resolution between the main peak and the closest impurity has narrowed, and one instrument runs consistently different from the other two.

You find out when an OOS forces a method investigation, and the first question anyone asks is how long this has been happening. Answering it means pulling every run of that method out of the LIMS, extracting the suitability parameters per injection, and building a picture by hand. That takes about a week, and it happens after the OOS rather than before it.

The information was there the whole time. It was in the same system, in the runs you already paid to execute, sitting one query away from being useful.

The demo

Every injection since validation, segmented four ways.

The agent is given a method. It reads every run of that method since validation, extracts the system suitability parameters per injection, then segments the population by column lot, instrument, analyst and reference standard lot to find which variable the drift tracks with, and shows the run at which it would first have been detectable.

Under the hood

The question is not whether it drifted. It is what it drifted with.

A single trend line across all runs is not much use, because a method can drift for four different reasons and the remedy is different for each. The value is in the segmentation, which is exactly the part that is too tedious to do by hand and trivial to do by query.

  • LIMS for every run of the method since validation, down to injection level: resolution, tailing factor, theoretical plates, replicate RSD, reference standard response and retention time.
  • Run metadata as the segmentation axes: column serial and lot, instrument, analyst, reference standard lot, mobile phase preparation and date.
  • Deterministic statistics per segment, calculated in code. Where a difference between instruments or analysts is reported, the underlying comparison is a query result rather than a model impression.
  • Earliest-detection point, which is the finding that changes behaviour: the run at which the drift would have been visible had anyone been looking, and what threshold would have caught it.
  • Cross-check against the validation report so current performance is compared to what was actually demonstrated at validation rather than to the acceptance criterion alone.

The agent describes the measurement system's behaviour and points at what the behaviour correlates with. Whether that constitutes a method investigation, a revalidation, a column change or nothing at all is an analytical judgement, and it stays with an AD scientist.

What it takes to get there

It depends on suitability data being queryable, not just archived.

Some LIMS and CDS configurations store system suitability as structured fields per injection. Others store the result and keep the parameters inside a PDF report attached to the run, which turns a query into an extraction problem. Column and instrument identifiers are the other common gap: if the column lot is recorded in an analyst's notebook rather than against the run, the most useful segmentation axis is not available.

The Data Diagnostic tells you which situation you are in for the methods you care about, and what it takes to close the gap, before you commit to a build.
