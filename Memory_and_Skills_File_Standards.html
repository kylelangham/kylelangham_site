Know which file you are writing

Wrong tier is a common failure problem

The dividing question is not importance, it is who is this true for. Anything true for everyone who touches the repo belongs in version control. Anything true only about one person's laptop does not. Be mindful of contradictory statements.

Repo root
./CLAUDE.md
What is true about this codebase for everyone. Commands, invariants, conventions, do-not-touch list.
Checked in. Reviewed.
Directory
src/<area>/CLAUDE.md
Rules that differ by subsystem. Firmware, data pipeline and the web tier rarely share review or test norms.
Checked in. Area owners.
User scope
~/.claude/CLAUDE.md
How this engineer works across every repo. Personal defaults, preferred output style, local tooling paths.
Not checked in. Templated and personalized.
Local override
./CLAUDE.local.md
One person's temporary situation in one repo. A broken dependency, a migration in flight, a scratch branch.
Gitignored. Short-lived.

Repo memory files

Treat as critical, not just documentation

What gets included

  • Exact commands. Build, test, lint, typecheck, single-test invocation. An agent that can verify its own work is worth more than one that writes better first drafts.
  • Invariants with the reason attached. "All timestamps stored UTC, converted at the edge" beats "be careful with time zones." A rule without a rationale gets rationalized around.
  • The do-not-touch list. Generated code, vendored dependencies, applied migrations, protobuf output.
  • Non-obvious local conventions. The pattern a competent new hire would violate on day one because it contradicts the framework default.
  • Known traps. The test that fails only in CI, the service that must be running first.

What does not — it competes for attention

  • Anything derivable from the code. Directory tours and dependency lists go stale within a sprint and the agent can read the tree.
  • General programming advice. "Write clean code," "handle errors properly." Zero behavioural effect, real attention cost.
  • Onboarding prose. Team history, product background, links to Confluence. Different audience, different document.
  • Aspirations. Standards you have not adopted yet produce output that does not match the repo it lands in.
  • Secrets or internal hostnames. This file is committed, read by tools, and pasted into issues.

Keeping it working

  • Directives, not description. Imperative voice, one instruction per line, testable. If you cannot tell whether the agent complied, rewrite it.
  • Prune on a schedule. Growth is the default and every stale line degrades the live ones. A line that has never changed an outcome is costing you in attention.
  • Fix in the file, not in the chat. When an agent does the wrong thing, the durable repair is a line in the memory file. Correcting it in conversation fixes it for one person once.
  • Watch for contradiction. Bloat rarely reads as wrong, it reads as two rules that cannot both hold.
  • Factor shared fragments. Where a standard spans repos, import a common file rather than copying it. Copies diverge silently.

Ownership and review

  • CODEOWNERS entry. No owner means no pruning.
  • Reviewed like an API change. One edit changes behaviour for everyone, on every task, silently.
  • Definition of done includes it. Change a convention, update the file in the same PR.
  • Announce material edits. People will otherwise attribute the change to the model.
  • Need help getting started? Point a chat window at your repo and ask your model to create a repo memory file. Personalize from there.

Failure modes

  • The write-once file. Created in a burst of enthusiasm, never touched again.
  • The kitchen sink. Everything anyone ever wished the agent knew. Instructions compete, adherence becomes unpredictable, and the file is now too big for anyone to review honestly.
  • Rules with no consequence. If nothing in CI or review catches a violation, the instruction is a suggestion. State it, then gate it.

Local files and harness standardization

The goal is identical behaviour, not identical laptops

Local configuration is where teams lose reproducibility. For example, the same prompt against the same repo produces different results for two engineers. You cannot check these files in, so standardize the way you standardize dotfiles: ship a reviewed template, make adoption one command, and audit for drift.

How to standardize what you cannot commit

  • Commit a template, not the file. Keep templates/claude-user.md and a settings template in the repo. The install step copies them into user scope. The template is reviewed; the copy is not.
  • Version the template. Put a version line at the top. A one-line check in CI or the dev script tells people when theirs is behind.
  • Bootstrap in one command. Add it to the existing dev setup script. Any standard requiring a wiki page and manual steps reaches roughly half the team.
  • Split team settings from personal. Checked-in project settings carry permission rules, hooks and approved tool servers. The gitignored local settings file carries only paths and personal preference.
  • Audit for drift quarterly. Ask people to diff their user file against the template. Recurring local overrides are a signal the template is wrong — promote them, do not police them.

What belongs in the local tier

  • Permission allowlists and denylists for shell commands the agent may run unattended
  • Approved tool and MCP server list, with anything reaching production or customer data excluded by default
  • Environment variable names and local service ports — names, never values
  • Output preferences: verbosity, commit message style, whether to open PRs automatically
  • Hooks that run formatters or tests after edits, so every engineer's agent self-checks the same way

What never does

  • Credentials, tokens or keys in any form, including "temporary" ones
  • Rules about the codebase itself — those belong in the repo file where review can see them

Skills files

A memory file shapes every task; a skill fires on one

Writing one that actually fires

  • The description is the product. It is the only part read when deciding whether to load the skill. Spend more time on it than on the body.
  • Trigger on the words people really use. List the phrasings verbatim, including sloppy ones. Abstract descriptions do not match concrete requests.
  • State the negative scope. "Do not use for X, use Y instead." Without it, a broad skill fires on everything and starves the specific ones.
  • One skill, one job. Overlapping skills compete and selection becomes a coin flip nobody can debug.
  • Deterministic steps, exact commands. The value is repeatability. Prose advice belongs in the memory file.
  • Specify the output shape. Name the table, sections or artifact required. Comparable output across runs and people is most of the payoff.
  • Keep the body short, link the depth. A tight procedure that references longer files on demand beats one long file loaded every time.

Operating them as a team

  • Version controlled and owned like any other source, in the repo where the work happens.
  • Test firing and non-firing. Collect real requests that should trigger it and near-misses that should not. Vague descriptions fail silently by never loading.
  • Re-test when you add neighbours. A new skill can steal triggers from an existing one.
  • Retire deliberately. A skill encoding a process you have replaced is worse than none.
  • Sandbox anything with side effects. A skill that runs commands inherits the agent's permissions, so scope it there rather than trusting the text.
The promotion path — how a private trick becomes a standard
1 · Personal
One engineer works out a prompt or loop that reliably produces good output.
2 · Shared command
Checked into the repo so anyone can run it. Still optional, still cheap to delete.
3 · Skill
Used often enough to deserve automatic triggering and a defined output shape.
4 · Memory file
True on every task in the repo, not just this one. The most expensive tier — earn it.
Run it in that order. Most teams invert it, starting with a large memory file assembled from opinions rather than evidence. Working upward means every line in the most expensive tier got there because it demonstrably changed an outcome, and the promotion step is also the review step.

Adoption checklist

Sequential — each row depends on the one above
Repo memory file exists, under CODEOWNERS, reviewed in PR
User-scope template committed, versioned, installed by the dev script
Exact build, test and lint commands present and verified current
Permission allowlist and denylist defined for unattended commands
Do-not-touch list explicit
Approved tool and MCP server list maintained, additions reviewed
Directory-level files where subsystem norms genuinely differ
Skills stored in repo, owned, with trigger and non-trigger cases tested
Updating the memory file is part of the definition of done
Quarterly prune of memory files and drift audit of local overrides
