Quick Start

Connecting Internal Data to AI Getting one real question answered from your own data, end to end, in an afternoon

Kyle Langham
Consulting

The key architectural concept is the model doesn't touch the data sources. Instead, you give the model access to tools, which can run bounded queries, and the result comes back as text and context for the model. What follows is a quick start, not the comprehensive version.

Layer 1

Source and transformation

BigQuery, dbt, Python, API...
Extract and model the data so column names and descriptions carry meaning.
Fails as: unreadable schema
Layer 2

Curated semantic layer

A narrow set of documented views the AI is allowed to see, with each metric defined exactly once.
Fails as: confident wrong numbers
Layer 3

MCP server or connector

Read-only, scoped, limit-bound access exposed as tools. This layer connects the AI model to the extraction layer.
Fails as: cost and exposure
Layer 4

Skill

Instructions covering how the work should be executed and how the output should be given.
Fails as: inconsistent answers

The build

(AI writes most of the code... see example prompts below)
What you doDone when
1

Pick the question and manually find the data

You need a number you can check against, otherwise you have no way to tell whether any of this worked. Note the tables it comes from and record the answer you expect.
You have a question, a source, and an expected answer.
2

Get to a working query

Paste the schema and column descriptions into the AI and have it write the query. Then read what it assumed about dates, filters and exclusions (it won't always flag it). If the data isn't already sitting somewhere queryable, this is where you write the Python extraction instead.
Running it by hand gives you the number from step one.
3

Wrap it as a local MCP server

Give the AI your working query plus a plain description of what this data does and doesn't cover, and ask for a local server that exposes it as a tool.
The model answers your question through the tool, with no data pasted into the chat.
4

Write a skill around a routine

Pick something you do over and over, like a weekly report or a recurring check. The skill covers when it fires, which tool it calls, which definitions apply, and what has to appear in the answer. Have the AI draft it, then edit it.
You ask in your own words on two different days and get the same number and the same query.
5

Try to break it

Ask five more questions you already know the answers to. Then ask some the data can't support to see if the model will guess confidently or return that no data is found.
The checkable answers are right, and the unanswerable ones come back as a no.

What to ask for — paste these, fill in the brackets

Step 2 · the query
Here's the schema and the column descriptions. Write a query that answers [question]. Before the code, list every assumption you made about dates, filters and what to exclude, so I can tell you what you got wrong.
Step 2 · extraction, if you need it
Write a Python function that connects to [source], runs this query and returns the result. Pull credentials from environment variables. Don't put them in the code.
Step 3 · the server
Here's my working function. Wrap it in a local MCP server with one read-only tool. In the tool description, say what subject it covers, what date range it has, and what it can't answer.
Step 4 · the skill
Write a skill for [routine] that uses this tool. Every answer needs the number, the query behind it, and the row count. If the data can't answer, it should say so instead of estimating.

Keep out, even on day one

  • Credentials in code. Environment variables from the start. The AI will hardcode them if you don't tell it not to.
  • Write access. Read-only account. Nothing in this path should be able to change anything.
  • PII. If it's in the table, strip it in the query before the tool ever sees it.
  • Other people using it. The server runs on your machine with your access. Once a second person needs it, you're building the real version.
Considerations when you need to scale this approach
Agree the definitions
Get the metric logic written down and signed off by whoever owns the number... once it's automated, changing it is a project.
Curated views, not a tool per question
A documented view layer lets one tool cover many questions.
Host it and scope it
Move off your laptop to a shared server with its own read-only account, byte and row caps, and query logs.
Keep a standing eval
Known answers you re-run whenever a schema or a skill changes, so a silent break or drift shows up in your test.
The trigger is usually a second person wanting access, not a technical limit. That's the point to stop extending the prototype and scope the real build, because everything above needs an owner and a budget rather than an afternoon.
